1. Introducción y alcance
Este documento describe la API REST de VoxReady, la plataforma de entrenamiento de vocería que evalúa el desempeño multimodal (voz, imagen y contenido) de un portavoz ante entrevistas simuladas. La especificación cubre los tres roles del producto y está pensada para desplegarse sobre Microsoft Azure.
La API se organiza por dominios funcionales que reflejan los flujos del producto: identidad, flujo del vocero (escenarios, sesiones, análisis, informes y progreso), administración del cliente (temas, retención y privacidad) y configuración maestra (rúbrica y cola de etiquetado).
Roles del sistema:
Vocero (spokesperson): practica escenarios, recibe informes y gestiona su progreso.
Admin del cliente (client_admin): gestiona temas, usuarios, uso y política de retención de su organización.
Configurador maestro (master_config): mantiene la rúbrica global y la cola de revisión; es el equipo central de VoxReady.
2. Arquitectura en Azure
La API se expone tras Azure API Management y se ejecuta sobre servicios gestionados de Azure. El siguiente cuadro resume el mapeo entre responsabilidades y servicios.
3. Convenciones generales
URL base: https://api.voxready.io  (todos los recursos cuelgan del prefijo de versión /v1).
Versionado: por ruta (/v1). Los cambios incompatibles incrementan la versión mayor.
Formato: JSON en peticiones y respuestas. Cabecera Content-Type: application/json.
Codificación de fechas: ISO 8601 en UTC (p. ej. 2026-06-25T14:30:00Z).
Identificadores: UUID v4 en formato string.
Idiomas: parámetro/atributo language con valores es, en, pt.
Paginación: parámetros page y pageSize; la respuesta incluye total.
Idempotencia: en operaciones POST sensibles se admite la cabecera Idempotency-Key.
Correlación: cada respuesta incluye la cabecera x-correlation-id para trazabilidad.
4. Autenticación y autorización
La autenticación se realiza con Azure AD B2C mediante OAuth 2.0 / OpenID Connect. El cliente obtiene un token de acceso (JWT) del proveedor de identidad y lo envía en cada solicitud:
Authorization: Bearer <access_token>
El token incluye el rol del usuario en un claim (por ejemplo extension_role) y un conjunto de scopes que API Management valida antes de enrutar. Cada endpoint declara el rol y el scope requeridos en su descripción.
Reglas de autorización principales:
El vocero solo accede a sus propios recursos (sesiones, progreso, grabaciones).
El admin del cliente solo opera sobre el clientId de su token (aislamiento por tenant).
El configurador maestro accede a recursos transversales (rúbrica, cola de etiquetado, métricas globales).
Un token válido pero con rol/scope insuficiente produce 403 forbidden; un token ausente o inválido produce 401 unauthorized.
5. Modelo de errores
Todas las respuestas de error usan el formato Problem Details (RFC 7807) con Content-Type application/problem+json. La estructura común es:
{
  "type": "https://api.voxready.io/errors/invalid_request",
  "title": "invalid_request",
  "status": 400,
  "detail": "El campo 'scenarioId' es obligatorio.",
  "correlationId": "b1f4-...",
  "errors": [ { "field": "scenarioId", "message": "requerido" } ]
}

Parámetros de entrada
Respuesta 200 OK

GET  /v1/scenarios/{scenarioId}
Obtiene el detalle de un escenario, incluyendo su contexto, óptica institucional, número de preguntas y duración estimada.
Rol requerido: Vocero    Scope: scenarios.read
Parámetros de entrada
Respuesta 200 OK
Mensajes de error
POST  /v1/sessions
Crea una sesión de práctica a partir de un escenario. Genera el conjunto de preguntas del entrevistador IA y deja la sesión en estado 'created', a la espera del consentimiento y la comprobación técnica.
Rol requerido: Vocero    Scope: sessions.write
Parámetros de entrada
Ejemplo de cuerpo (request)
{ "scenarioId": "c7d2...", "language": "es" }
Respuesta 201 Created
Mensajes de error
Nota: El cuerpo de las preguntas no se entrega de antemano; se transmiten durante la sesión en vivo para preservar el realismo.
POST  /v1/sessions/{sessionId}/consent
Registra el consentimiento biométrico del vocero (grabación de voz e imagen) según la política de retención del cliente. Es obligatorio antes de iniciar la grabación (UK GDPR).
Rol requerido: Vocero    Scope: sessions.write
Parámetros de entrada
Ejemplo de cuerpo (request)
{
  "acceptRecording": true,
  "acknowledgeDeletion": true,
  "policyVersion": "ret-2026-01"
}
Respuesta 200 OK
Mensajes de error
POST  /v1/sessions/{sessionId}/recording-url
Solicita una URL de carga (SAS de escritura sobre Azure Blob Storage) para subir la grabación de la sesión. La URL es de un solo uso y caduca.
Rol requerido: Vocero    Scope: sessions.write
Parámetros de entrada
Ejemplo de cuerpo (request)
{ "contentType": "video/webm", "durationSeconds": 312 }
Respuesta 200 OK
Mensajes de error
Nota: El cliente sube el archivo directamente a Blob Storage con la SAS; el backend nunca recibe el binario, lo que reduce carga y costo de egreso.
POST  /v1/sessions/{sessionId}/finish
Marca la grabación como completa y encola el análisis multimodal asíncrono (voz, imagen, contenido y fusión de empatía) en Azure Service Bus. Devuelve el identificador del trabajo de análisis.
Rol requerido: Vocero    Scope: sessions.write
Parámetros de entrada
Ejemplo de cuerpo (request)
{ "blobPath": "rec/2026/06/sess-c7d2.webm" }
Respuesta 202 Accepted
Mensajes de error
Nota: Análisis asíncrono: usar GET /analysis para sondear (polling) o suscribirse al webhook session.analysis.completed.
GET  /v1/sessions/{sessionId}/analysis
Consulta el estado del análisis multimodal de una sesión. Permite mostrar la pantalla 'Analizando…' con el progreso de cada pipeline.
Rol requerido: Vocero    Scope: sessions.read
Parámetros de entrada
Respuesta 200 OK

10. Webhooks / eventos
VoxReady publica eventos mediante Azure Event Grid para notificar el fin del análisis sin necesidad de polling. El cliente registra un endpoint HTTPS que recibe un POST con el evento.
session.analysis.completed
Se emite cuando el análisis multimodal de una sesión finaliza y el informe queda disponible.
{
  "eventType": "session.analysis.completed",
  "sessionId": "c7d2...",
  "analysisId": "9a01...",
  "status": "completed",
  "reportReady": true,
  "occurredAt": "2026-06-25T14:31:07Z"
}
El receptor debe responder 2xx en menos de 30 segundos; Event Grid reintdenta con backoff si falla. La autenticidad se valida con la clave de validación de Event Grid o un encabezado de firma compartido.
session.analysis.failed
Se emite si algún pipeline falla de forma irrecuperable. Incluye failureReason. El vocero puede reintentar la sesión.
