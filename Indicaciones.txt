### 2. Tarea 1: Cálculo Real de Dicción Fonética (`audio_analyzer.py`)

#### Contexto del problema

El reporte actual devuelve un valor estático fijado en `"score_diccion": 100.0` sin procesar la calidad acústica de las palabras.

#### Implementación técnica

1. **Extracción de confianza en Parakeet:**
La respuesta estructurada de Parakeet-TDT expone para cada palabra transcrita su marca temporal y su nivel de certeza acústica ($\text{confidence} \in [0.0, 1.0]$).


2. **Algoritmo de cálculo:**
En `services/audio_analyzer.py`, sustituir el valor hardcodeado por el promedio aritmético de confianza escalado a base 100, descartando palabras vacías o símbolos de puntuación:
$$\text{score\_diccion} = \left( \frac{1}{N} \sum_{i=1}^{N} \text{confidence}_i \right) \times 100$$



```python
def compute_diction_score(parakeet_words: list[dict]) -> float:
    """
    Calcula la claridad fonética basada en la confianza acústica de Parakeet.
    Cada elemento en parakeet_words debe contener 'word' y 'confidence'.
    """
    valid_confidences = [
        float(w["confidence"]) 
        for w in parakeet_words 
        if "confidence" in w and w.get("word", "").strip()
    ]
    
    if not valid_confidences:
        return 70.0  # Fallback defensivo si no hay palabras reconocibles
    
    mean_confidence = sum(valid_confidences) / len(valid_confidences)
    return round(mean_confidence * 100, 1)

```

3. **Integración en la nota de Voz (`area_score.voice`):**
En `report_builder.py`, ponderar el `score_diccion` dentro del cálculo del canal auditivo:


$$\text{Score Voz} = (\text{Puntaje WPM} \times 0.40) + (\text{Score Fluidez} \times 0.35) + (\text{Score Dicción} \times 0.25)$$

### 3. Tarea 2: Extracción e Inyección de Líneas Rojas (`llm_judge.py`)

#### Contexto del problema

El catálogo del administrador permite configurar "Líneas Rojas" (frases, justificaciones o admisiones legales estrictamente prohibidas para el vocero). Actualmente, el Juez LLM evalúa apego a mensajes clave, pero no penaliza de forma determinista la transgresión de estas prohibiciones.

#### Implementación técnica

1. **Lectura desde base de datos (`database.py`):**
Al inicio del pipeline, el worker debe consultar las líneas rojas vinculadas al escenario que se está analizando mediante su relación con `topic`:


```sql
SELECT rl.text 
FROM red_line rl
INNER JOIN topic t ON rl.topic_id = t.id
INNER JOIN scenario s ON s.topic_id = t.id
WHERE s.id = :scenario_id
ORDER BY rl.sort_order ASC;
```[cite: 7]

En `services/llm_judge.py`, inyectar la lista de líneas rojas en el bloque de instrucciones para `meta/llama-3.2-90b-vision-instruct`:



```markdown
LÍNEAS ROJAS DEL ESCENARIO (ESTRICTAMENTE PROHIBIDAS):
{% for rl in red_lines %}
- "{{ rl }}"

REGLA CRÍTICA DE EVALUACIÓN:

### 4. Tarea 3: Reconocimiento Explícito del Afectado (`llm_judge.py`)

#### Contexto del problema

La rúbrica de crisis de Visum exige evaluar si el vocero coloca a las víctimas o clientes afectados como la primera prioridad comunicacional antes de presentar defensas corporativas o balances técnicos. En el esquema actual, la nota de Empatía depende casi exclusivamente de correlaciones matemáticas con la mirada y la postura.

#### Implementación técnica

1. **Nueva dimensión en el LLM Juez:**
Incorporar en el prompt de evaluación la variable `reconocimiento_afectados` (escala 1 a 5):



```markdown
DIMENSIÓN ADICIONAL - RECONOCIMIENTO DEL AFECTADO:
- Nivel 5: Prioriza inmediatamente el impacto humano, a los clientes perjudicados o a la comunidad antes de dar explicaciones técnicas o corporativas. Muestra empatía activa sin evasivas.
- Nivel 3: Menciona a los afectados de forma tardía o como una formalidad secundaria.
- Nivel 1: Ignora el impacto humano; se enfoca exclusivamente en justificaciones financieras, operacionales o en deslindar responsabilidades corporativas.

```

2. **Cálculo Híbrido de Empatía en `report_builder.py`:**
Reestructurar el cálculo del área `empathy` combinando la señal no verbal (congruencia de mirada y estabilidad) con la señal verbal (reconocimiento evaluado por el LLM):


$$\text{Score Empatía Verbal} = \left(\frac{\text{Nivel Reconocimiento} - 1}{4}\right) \times 100$$


$$\text{Score Empatía Final} = (\text{Empatía No Verbal} \times 0.40) + (\text{Score Empatía Verbal} \times 0.60)$$

### 6. Criterios de Aceptación (DoD) para QA y Testing

1. **Prueba de Dicción Real (`audio_analyzer_test.py`):**  
   Al inyectar un payload de Parakeet con confianza media de $0.85$, el campo `metrics.audio.scoreDiccion` debe registrar exactamente `85.0` (eliminando el valor fijo de `100.0`)[cite: 2].
2. **Prueba de Transgresión de Línea Roja (`llm_judge_test.py`):**  
   Ejecutar una evaluación con una transcripción que contenga deliberadamente una frase prohibida (ej. *"No habrá indemnizaciones"*)[cite: 7]. Verificar que `infraccionLineaRoja` sea `true`, que `consistencia_institucional` caiga a nivel 1 y que el puntaje final de Coherencia quede truncado a un máximo de 20 puntos[cite: 2, 7].
3. **Prueba de Empatía Cruzada:**  
   Verificar que una respuesta con 100% de contacto visual pero con omisión total de las víctimas no obtenga un puntaje de Empatía superior a 40 puntos[cite: 2].
4. **Tiempo de Ejecución:**  
   El pipeline completo debe mantenerse por debajo de los 60 segundos totales de procesamiento en Azure Container Apps[cite: 4, 5].
