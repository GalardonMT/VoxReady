### Especificación Técnica de Implementación: Montaje y Persistencia del Reporte Final de Sesión (Opción 1)

**Para:** Equipo de Ingeniería (*Antigravity*)

**Módulos Afectados:** `ca-analysis-worker` (Capa de Fusión y Datos), `ca-backend-api` (Endpoints de Reporte), `sqldb-voxready` (Persistencia Relacional).

**Objetivo:** Consolidar el pipeline de análisis multimodal en un único informe global por entrevista, sanear las redundancias del objeto JSON de salida, persistir los resultados en el esquema relacional existente de Azure SQL y exponer el contrato enriquecido hacia el frontend.

---

### 1. Diagnóstico y Saneamiento del JSON en el Worker (`report_builder.py`)

El JSON generado actualmente por la capa de fusión contiene todas las métricas requeridas por Visum, pero presenta duplicidades críticas que deben eliminarse antes de insertarlo en base de datos o enviarlo a la red:

1. **Eliminar redundancia de Visum:** Suprimir el nodo raíz `informe_ejecutivo_visum`, conservando únicamente `narrative.visum`.
2. **Unificar nombres de métricas de visión:** Eliminar claves duplicadas en español (`contacto_visual_porcentaje`, `average_posture_score`, `total_frames_analizados`) y retener únicamente el estándar técnico en `metrics.vision`:
* `eye_contact_pct` (float)
* `shoulder_stability_score` (float)
* `body_sway_std` (float)
* `hands_visible_pct` (float)
* `frames_analyzed` (int)


3. **Consolidar dimensiones del Juez:** Preservar `metrics.judge.dimensiones` y `metrics.judge.feedback`, eliminando la copia cruda redundante `metrics.judge.raw_evaluation`.

### 2. Mapeo y Persistencia en Azure SQL (`sqldb-voxready`)

La persistencia debe ejecutarse dentro de una única transacción atómica en `ca-analysis-worker/services/database.py` al concluir el análisis, mapeando hacia las tablas del modelo relacional existente:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        TRANSACCIÓN SQL (Worker)                        │
├──────────────────────────────────┬─────────────────────────────────────┤
│ 1. INSERT INTO report            │ Cabecera, overall_score y texto     │
│ 2. INSERT INTO area_score (x4)   │ Filas: expression, voice, etc.      │
│ 3. INSERT INTO                   │                                     │
│    analysis_pipeline_result      │ summary_json = JSON completo        │
│ 4. UPDATE session                │ status = 'completed'                │
└──────────────────────────────────┴─────────────────────────────────────┘

```

#### A. Inserción en tabla `report`

### 3. Exposición en el Backend (`ca-backend-api`)

#### A. Actualización de ruta `GET /v1/sessions/{sessionId}/report`

El endpoint (correspondiente a la tarea `RPT-1` del sprint) debe consultar la vista consolidada combinando los datos tabulares de `report` con el `summary_json` de la ejecución:

```python
@router.get("/v1/sessions/{session_id}/report", response_model=SessionReportResponse)
async def get_session_report(
    session_id: UUID,
    db: AsyncSession = Depends(get_db_session),
    current_user: TokenData = Depends(get_current_user)
):
    # 1. Validar que la sesión exista, pertenezca al usuario (o admin) y esté 'completed'
    session = await crud_session.get_by_id(db, session_id, user_id=current_user.sub)
    if not session:
        raise HTTPException(status_code=404, detail="Sesión no encontrada")
    if session.status != "completed":
        raise HTTPException(status_code=409, detail="El análisis de la sesión no ha finalizado")

    # 2. Consultar el reporte vigente (is_current = 1) y sus area_scores
    report = await crud_report.get_current_by_session(db, session_id)
    area_scores = await crud_report.get_area_scores(db, report.id)

    # 3. Extraer el blob de métricas técnicas enriquecidas desde analysis_pipeline_result
    pipeline_res = await crud_pipeline.get_fusion_result(db, report.analysis_job_id)
    extra_data = json.loads(pipeline_res.summary_json) if pipeline_res else {}

    # 4. Generar URL SAS de lectura temporal para el video (si la retención lo autoriza)
    recording_url = generate_read_sas_url(session.blob_path, duration_minutes=60)

    # 5. Mapear respuesta compatible OpenAPI
    return {
        "sessionId": session.id,
        "overallScore": report.overall_score,
        "scenarioTitle": session.scenario.title,
        "generatedAt": report.generated_at.isoformat(),
        "recordingUrl": recording_url,
        "narrative": {
            "strengths": json.loads(report.narrative_strengths) if isinstance(report.narrative_strengths, str) else report.narrative_strengths,
            "improvements": json.loads(report.narrative_improvements) if isinstance(report.narrative_improvements, str) else report.narrative_improvements,
            "crossSignal": report.cross_signal_observation
        },
        "areaScores": [
            {"area": a.area, "value": a.value} for a in area_scores
        ],
        "visumExecutive": extra_data.get("narrative", {}).get("visum", {}),
        "metricsSummary": {
            "eyeContactPct": extra_data.get("metrics", {}).get("vision", {}).get("eyeContactPct"),
            "shoulderStabilityScore": extra_data.get("metrics", {}).get("vision", {}).get("shoulderStabilityScore"),
            "wpm": extra_data.get("metrics", {}).get("audio", {}).get("wpmGlobal"),
            "fillerWordsCount": len(extra_data.get("metrics", {}).get("audio", {}).get("muletillasDetectadas", [])),
            "fillerWordsDensityPct": extra_data.get("metrics", {}).get("audio", {}).get("densidadMuletillasPct")
        }
    }

```

### 5. Criterios de Validación Técnica y QA

1. **Persistencia limpia:** Al invocar `POST /analyze` en el worker, confirmar que la tabla `report` recibe una fila válida, `area_score` recibe exactamente 4 filas vinculadas, y `analysis_pipeline_result` almacena el JSON saneado sin campos duplicados.


2. **Consistencia de claves foráneas:** Los valores insertados en `area_score` deben coincidir con las 4 áreas activas de la versión de rúbrica en `rubric_area` (`expression`, `voice`, `coherence`, `empathy`).


3. **Resiliencia de Endpoint:** `GET /v1/sessions/{id}/report` debe responder en menos de 200 ms, entregando una URL SAS de lectura válida para el video y parseando los atributos `narrative` sin errores de serialización.


4. **Manejo de estados:** Si la sesión se encuentra en estado `analyzing` o `created`, el backend debe rechazar la consulta del reporte con código `HTTP 409 Conflict` bajo el estándar RFC 7807.
